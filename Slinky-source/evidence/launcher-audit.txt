Independent launcher audit; static analysis only. Original Slinky.exe was read as bytes by pefile/Capstone and not executed. Findings corroborate IDA decompilation with original-machine-code disassembly in work/launcher-disasm.txt. Image base 0x140000000. Scope: EXE launcher and its imports; embedded DLL internals belong to separate analysis.

E-LA1 Artifact: SHA256 501d7c83e2010937350fee800e37631e1499ec9b2693a32493db71e5f40b0272; 6,549,504 bytes; native x64 GUI PE. The 6,404,096-byte RCDATA resource ID 200 is itself a PE (MZ prefix), SHA256 863a709c0c8ed82dbcfc98f118d64cfeb40c738efcee1d8f4b0bfd6f857f0d6f. It comprises most of the EXE.

E-LA2 Extraction: WinMain 0x140001000 gets resource type 10, ID 200 at 0x140001048, SizeofResource at 0x14000105F, LoadResource at 0x14000106C, LockResource at 0x14000107E. GetTempPathW at 0x1400010A4 and launcher PID at 0x1400010AA form %TEMP%\\slinky-<launcher PID> via format %lsslinky-%lu; CreateDirectoryW at 0x1400010E2. The next format creates \\SlinkyNative.dll, CreateFileW 0x140001137 uses GENERIC_WRITE, no sharing, CREATE_ALWAYS, FILE_ATTRIBUTE_NORMAL. WriteFile at 0x14000115D writes the exact resource bytes and count check at 0x14000116C verifies length. No target launch is required to establish this behavior; it is statically visible. No deletion of dropped file or directory is visible in launcher application code/imports.

E-LA3 Target selection: sub_140001490 enumerates processes (CreateToolhelp32Snapshot flags 2 at 0x1400014C8). Case-insensitive compare routine sub_140005720, with ASCII case folding visible in sub_1400056C0, selects executable names java.exe/javaw.exe via calls 0x140001516/0x14000152B. It records at most 64 candidates (capacity argument in WinMain 0x14000117D). EnumWindows at 0x1400015A2 and callback 0x140001690 attach the first visible nonempty top-level window title matching a candidate PID; entries without a title are removed at 0x1400015C0. There is NO comparison of window title to Minecraft and NO verification of Minecraft 1.8.9 in this selection logic. Calling the count 'Minecraft windows' is UI wording, not a detection guarantee. A different visible Java application can meet the launcher filter.

E-LA4 UX: If exactly one candidate exists on launch, WinMain calls inject at 0x1400011A8 automatically. Otherwise, UI is 'Slinky – Select Minecraft', listbox, Inject, Cancel, status 'Waiting for Minecraft to open...'. 750 ms timer refreshes list. In WndProc, a transition from previous candidate count zero to current count one calls inject automatically at 0x140001D4A. An explicit Inject button also does so at 0x140001D9B. On successful injection/already-present result the launcher exits. Error text requests Administrator and Minecraft 1.8.9; executable manifest declares asInvoker, uiAccess=false, so it does NOT automatically request elevation. No ShellExecute/RunAs or elevation implementation in launcher imports/custom logic.

E-LA5 Injection: sub_140001780 accepts PID and absolute dropped DLL path. Duplicate-presence helper sub_1400019F0 enumerates target modules and case-insensitively compares the complete szExePath against this DLL path, returning module base. It returns status 2 if already present. OpenProcess at 0x1400017E9 requests 0x43A = PROCESS_CREATE_THREAD | PROCESS_VM_OPERATION | PROCESS_VM_READ | PROCESS_VM_WRITE | PROCESS_QUERY_INFORMATION. VirtualAllocEx 0x140001819 requests MEM_COMMIT|MEM_RESERVE, PAGE_READWRITE for a UTF16 DLL-path string including NUL; WriteProcessMemory 0x140001841 writes that string. This is NOT an executable shellcode allocation. GetModuleHandleW(kernel32.dll) 0x140001871 and GetProcAddress(LoadLibraryW) 0x140001884 get local addresses; toolhelp target-module enumeration locates remote kernel32 base. CreateRemoteThread at 0x14000192F uses local LoadLibraryW address + remote kernel32 base - local kernel32 base as thread entry, with remote DLL-path buffer as argument. Thus conventional LoadLibraryW DLL injection, not process hollowing or manual mapping. It waits 30 seconds (WaitForSingleObject 0x140001945), then checks for the module up to 100 times with Sleep(50 ms) at 0x140001966. Success means the DLL's module path appears, not proof all DLL initialization/features succeeded. It frees remote path storage and closes handles; it does not unload the injected DLL. NOTE: correctness of the local-to-remote RVA assumption on an actual OS was not tested.

E-LA6 Decompiler corrections: Hex-Rays displays sub_1400019F0(th32ProcessID) with path argument omitted at the two call sites. Machine code explicitly puts saved DLL path in RDX at 0x1400017B0 and 0x140001951 before calls 0x1400017C3/0x140001957. Therefore there is no uninitialized path argument bug established by the pseudocode. Hex-Rays likewise omits third bounded-copy count argument in some calls to sub_140005550; original machine code passes R8D=0x103 at 0x14000154D, and callback copies window title with a count as well. Pseudocode format helper types cast 64-bit pointers to int: original x64 call sites use RCX and R9 full pointers; this is inferred type loss, not pointer truncation in the executable.

E-LA7 Bounded negatives: Launcher import table contains KERNEL32, USER32, GDI32 only. Its custom main/control code at 0x140001000-0x14000202C contains extraction, process/window enumeration, UI and injection. No networking, download, credential collection, encryption/ransom, service installation, scheduled task, registry autorun, Startup-folder write, or shell-spawn behavior identified in that custom launcher flow. Imported GetProcAddress has application use to resolve LoadLibraryW; remaining xrefs include CRT try_get_function/try_cor_exit_process paths and generic runtime code. IsDebuggerPresent import is referenced by CRT/error-reporting functions at 0x14000294B/0x140009B43; its existence alone does not establish custom anti-debugging. FindFirstFileExW belongs to argument wildcard expansion. Generic CRT VirtualProtect or file APIs alone are not evidence of malicious behavior. Negatives DO NOT apply to embedded DLL, opaque data or runtime behavior; launcher analysis cannot declare the whole package safe.

Assessment: The launcher demonstrably acts as a DLL dropper/injector for a Java process, branded as a Minecraft client. That mechanism is common to game cheats/mod injectors and malware alike and is not alone sufficient to classify as a RAT/stealer. The embedded DLL is the decisive remaining analysis surface.
